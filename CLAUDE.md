# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # start dev server (localhost:3000)
npm run build    # production build
npm run lint     # ESLint (must pass with 0 problems)
npm run start    # serve production build
npm run storyboards   # fetch YouTube storyboards for videos added to lib/video-data.ts
```

**E2E tests** use Playwright:
```bash
npx playwright install chromium   # first time only
npx playwright test               # run all tests (starts dev server automatically)
npx playwright test e2e/navigation.spec.ts --project=chromium  # single file
```

Tests live in `e2e/` covering navigation, Shorts player, video detail, responsive layouts, and the YouTube-style UI rules (`e2e/ui.spec.ts`). `e2e/fake-youtube.ts` replaces the YouTube embed with a fake player that speaks the same postMessage protocol (and can end a video), used by `e2e/shorts-playback.spec.ts` (autoplay/mute rules, lost play commands), `e2e/watch-page.spec.ts` (player size, end screen, playlist autoplay, opening a linked short) `e2e/inline-preview.spec.ts` (inline playback in cards: hover, progress bar geometry and seeking, on-screen autoplay, touch and hold, the Settings switch) and `e2e/ios-playback.spec.ts` (WebKit with an iPhone profile: a tap on a card, on Shorts or on a short card plays with sound in the shared player, and the next short keeps it). The fake starts muted when the embed URL says `mute=1`, plays at once with `autoplay=1`, takes `loadVideoById` and reports `videoData.video_id`; `{ ios: true }` models Safari (no sound for a player started on its own, sound for good once `unMute` reaches a playing player). `e2e/progress.spec.ts` covers watched progress (red bars, going on from the saved place, History, playing in a card; the fake's `{ clock: true }` lets time run while it plays). `e2e/qa.spec.ts` covers History on phones, the first tap opening a card, the watch controls hiding on phones, the bottom nav and toast positions, Settings languages, the channels' Home feed button and real durations. `e2e/storyboard.spec.ts` covers the progress bars' storyboards (the sheets are mocked) and `e2e/click-ui.spec.ts` that a click leaves nothing behind (no focus border, no 3-dot still showing, no menu under its dialog). `e2e/menus.spec.ts` covers scrolling with a menu open, `e2e/messages.spec.ts` when a message shows and its Undo, `e2e/save-card.spec.ts` the Save card, and `e2e/player-controls.spec.ts` the watch player's controls. Results of larger changes are kept in `docs/test-results/`. Touch gestures (swipes, slow taps) use CDP `Input.dispatchTouchEvent`, so they run in Chromium only. The `playwright.config.ts` at project root auto-starts the dev server via `webServer` config with `reuseExistingServer: true`.

TypeScript build errors are suppressed (`typescript.ignoreBuildErrors: true` in `next.config.mjs`), so run `npx tsc --noEmit` to type-check (it should report 0 errors). `npm run lint` runs ESLint 9 with `eslint-config-next` (flat config in `eslint.config.mjs`; Next 16 removed `next lint`) and should pass with 0 problems. Generated shadcn code in `components/ui/` is excluded. The few `eslint-disable` comments each say why: mostly effects that read localStorage or the URL after hydration.

## Stack

- **Next.js 16** (App Router, Turbopack for `dev` and `build`), **React 19**, **TypeScript**, **Tailwind CSS v3**
- Server `layout.tsx` files must `await params` (Next 16 removed synchronous access); client pages use `useParams()`/`useSearchParams()`
- `next/image`: use the `preload` prop (`priority` is deprecated in Next 16)
- **shadcn/ui** (Radix UI primitives) — components live in `components/ui/`
- **lucide-react** for icons, **next-themes** for dark/light mode, **sonner** for toasts
- No backend, no API routes, no database — all data is static mock data

## Architecture

### Layout shell

`app/layout.tsx` composes the full shell in this order:

```
HeaderProvider
  AppHeader          (fixed top, 56px, z-40)
  DesktopSidebar     (fixed left, 240px/72px, z-30, hidden on video/playlist/signin pages)
  AppShell           (<main> that offsets left-padding to match sidebar width)
    {children}
  MobileNav          (fixed bottom bar, mobile only, hidden on detail/fullscreen pages; stays put while scrolling)
```

**AppShell** (`components/app-shell.tsx`) dynamically sets `md:pl-[240px]` or `md:pl-[72px]` on `<main>` by reading sidebar width from `window.__sidebarGetState`. The desktop sidebar and AppShell both listen to the custom `"sidebar-state-change"` window event to stay in sync.

### Sidebar communication (global window pattern)

The desktop sidebar exposes two globals set in a `useEffect`:

- `window.__sidebarToggle()` — toggles collapsed state; called only by the hamburger in `AppHeader`
- `window.__sidebarGetState()` — returns current `isCollapsed` boolean

Sidebar state is persisted to `localStorage` key `'sidebar-collapsed'`. The sidebar reads this on mount to restore state across navigations. The header hamburger button toggles the desktop sidebar on pages that have one. On `/videos/*` and `/playlists/*`, `DesktopSidebar` switches to overlay mode, so the hamburger slides the sidebar in over the content. `/signin` has no global header, sidebar or bottom nav. A script in `app/layout.tsx` applies the saved collapsed state before first paint (see the "Sidebar first paint" block in `app/globals.css`).

### Data layer

All data is static TypeScript arrays in `lib/`:

| File | Contents |
|---|---|
| `lib/video-data.ts` | `VideoItem[]` — main feed videos with YouTube video IDs. `duration` is the video's real length on YouTube (`"lengthSeconds"` on its watch page), so the card matches the player; the saved-list and history hooks take it from here, not from copies saved earlier |
| `lib/shorts-data.ts` | Shorts feed data |
| `lib/mock-data.ts` | Channels and scholars for listing pages |
| `lib/channel-data.ts` | Sidebar channel list |
| `lib/scholar-data.ts` | Sidebar scholar list |
| `lib/playlist-data.ts` | Static playlist definitions |
| `lib/storyboard-data.ts` | Each video's YouTube storyboard; generated by `npm run storyboards` (`scripts/storyboards.mjs`), don't edit |

All videos are YouTube embeds using `<iframe src="https://www.youtube.com/embed/{videoId}?...">`. On the Shorts page, iframes include `enablejsapi=1` and are controlled via the YouTube postMessage protocol (see Shorts page section below). The watch pages (video, playlist) use `components/youtube-player.tsx`: YouTube's privacy-enhanced embed (`www.youtube-nocookie.com`, which leaves out creators' end-screen cards, the video thumbnails the normal embed shows over a video's last seconds; same postMessage API, so the origin checks use that host) with **our own YouTube-style controls**. Shorts still use `www.youtube.com`. YouTube shows its suggestions (the "More videos" pill, share button, title bar) whenever the embed is paused and for a few seconds after playback starts, so: YouTube's controls are off (`controls=0`); a transparent layer over the frame takes every click and hover; and the frame is `CROP` (120px) taller than the box at the top and bottom, which cuts those edge overlays off while the video still fills the 16:9 box exactly. Only while captions are on and the video plays is the frame box-sized, because YouTube draws captions near its bottom edge. Our controls are YouTube's updated ones (measured on youtube.com and m.youtube.com): each group on its own rounded `bg-black/30` backing, no gradient. With a mouse (`can-hover:`): a 56px row of 40px groups, 12px in and 8px up: play + next; volume (its 52px slider opens on hover); the time (a click switches to the time left); then Autoplay, captions, settings and full screen in one group (`BarButton`: an inner highlight, and its name and key above the bar on hover). On touch screens: play (56px) and next in the middle, Autoplay, captions and settings in a group at the top right, the time and full screen above the bar, whose line is 22px from the bottom; no volume button (phones have keys). Plus a seekable progress bar with storyboards (see below), a settings menu (Autoplay, captions, speed; it scrolls when the player is too short for it) and full screen (on the player element, so the controls stay; iPhone, which can't, gets a fixed full-window player), plus YouTube's keys (space/k, j/l, ←/→, f, m, c). The thumbnail covers the player (`opacity-0`, for the same layout-shift reason as Shorts) until it plays; the handshake starts on mount as well as on load, because the server-rendered frame can load before React hydrates. Playback starts with `playVideo`; if YouTube reports `onAutoplayBlocked` it plays muted with a "Click to unmute" button. At the end our end screen covers YouTube's: "Up next in N" (8s countdown, Cancel, Play now) when Autoplay is on, else Replay and the "Up next" card. On touch screens the controls hide 3s after playback starts or after a tap (2.5s after the last mouse move with a mouse); only a mouse over the control bar keeps them up.

**iPhone, iPad and Safari: one shared player** (`lib/player-host.ts`, following Quran Tube, which was tested on real iPhones). WebKit only allows sound when a player that is already playing is unmuted inside the tap; a watch page's own new frame loads after the tap, so it would play muted with "Tap to unmute". So on those browsers (detected by user agent, `hostWanted()`; Chrome/Android/Firefox keep the page's own frame) one frame, created outside React at the end of `<body>` soon after load (`bootPlayerHost()` in `AppShell`), plays a muted placeholder video (`p3Mrisem6ek`, Deeni Info Tech) while hidden. A window click listener catches taps on any link to `/videos/<slug>/<id>`, `/shorts?v=<id>` or `/shorts` (its first short, `FIRST_SHORT_ID`; not on the Shorts page itself), or an element with `data-play-id`, and, inside the tap, sends `loadVideoById({ videoId })` (no `startSeconds`: it broke the swap on iPhones) → `unMute` → `playVideo`, then re-sends `unMute` for a few seconds if YouTube reports muted again. The watch player (`hosted` mode) renders no frame of its own: it attaches the shared frame, which is placed over its box in page coordinates (z-index 1, under the player root's own layer, `z-[2]` with a transparent background), and its controls drive it; the end screen's Next/Play now/Up next also go through `playFromTap`. Messages about another video (`videoData.video_id`) are ignored, so the placeholder never shows. Full screen fills the window (and asks for the whole page's full screen where possible), since the frame isn't inside the player element. When no watch page uses it, the frame hides, pauses, and goes back to the muted placeholder after 1.5s. Opened directly from a link (no tap in the app), the video still plays muted with "Tap to unmute"; that tap gives the shared player sound for the rest of the visit (`hostSoundAllowed()`; until then pages must not ask it for sound, which Safari answers by stopping the video). The Shorts page uses the same frame (see below). The video page's Autoplay switch is saved per device (`'deeni-autoplay'`); the playlist page passes its own (`autoplay`/`onAutoplayChange`) and moves on at once. On the video page "Up next" is the next video in catalogue order (the related list is rotated to start there). Their layout comes from `components/watch-layout.ts` (YouTube's: two columns from 1016px; the 16:9 player's height ≤ `100vh - 216px`, so the title and channel stay above the fold, never under 640px wide; a 402px side column that takes spare width only up to 480px, past which the player grows instead, so there's never empty space at the sides, as long as the player stays ≤ `100vh - 176px` tall; one column below 1016px). `<body>` uses `overflow-x: clip` (not `hidden`, which makes body a scroll container and silently breaks every `position: sticky`), and `app/globals.css` also keeps it that way while Radix menus/dialogs lock scrolling (`html body[data-scroll-locked]` overrides the lock's `overflow: hidden` and scrollbar `margin-right`, which made the related column jump and the page shift; the lock still blocks wheel/touch scrolling). The player box is always exactly `aspect-video` with no max-height, so YouTube never adds black side bars; on the video page it is one element placed with CSS (edge to edge on phones), not a JS phone/desktop switch, so the server HTML already shows it.

**Storyboards** (`lib/storyboard.ts`, `components/storyboard.tsx`): the frames YouTube shows while a progress bar is hovered or dragged, on the watch player and in playing cards. YouTube's sheets need a signed link from the video's watch page, so `npm run storyboards` fetches them into `lib/storyboard-data.ts` (run it after adding videos; the links don't expire: they are made once, when the video is processed, and come out the same every time). Nothing loads before the bar is used: then the data file (its own chunk) and the video's L0 sheet (25 KB, 100 tiny frames of the whole video), which shows at once under the sharper sheet. A video without one, or whose sheets can't load, shows just the time. All sizes were measured on youtube.com: the watch page's bar is 4px (6px under the pointer), 12px in from the sides and 56px above the bottom, its playhead 12px (20px); the box is a 240px frame in a 1px white border, 59px above the line, with the time in a pill between them; dragging also covers the video with the frame at 40% on black. In a card the box is a 90px tall frame in a 2px white border, 56px above the bottom edge, with the time under it; dragging covers the card with the frame and shows the time in the middle. With a finger the frame covers the whole player or card, and the watch page's buttons step aside. A press that moves less than 3px is a click: it seeks without covering anything. The video isn't paused while dragging (pausing makes YouTube draw its own icon over the frame).

### User state via localStorage

All user-generated state is persisted directly to `localStorage`:

| Key | Contents |
|---|---|
| `'sidebar-collapsed'` | Desktop sidebar state |
| `'deeni-lang-prefs'` | Auth/guest status (`{ isGuest: boolean }`) |
| `'recentSearches'` | Search history array |
| `'deeni-watch-later'` | Watch Later items (seeded with demo items on first visit) |
| `'deeni-liked-videos'` | Liked videos and shorts (seeded on first visit) |
| `'deeni-watch-history'` | Watch history, recorded by the video page, playlist player and Shorts (seeded from `lib/history-data.ts`) |
| `'deeni-playlists'` | All library playlists (seeded from `extendedPlaylists` on first visit; `videoIds` use internal ids like `"v3"`) |
| `'deeni-notification-prefs'` | Settings page notification toggles |
| `'feed-visible-channels'` | Channels shown in the home feed (`hooks/useFeedPreferences.ts`; "Don't recommend channel" removes one) |
| `'deeni-voice-lang'` | Voice search language (`en-US` or `bn-BD`), set in the voice search dialog |
| `'deeni-autoplay'` | The watch page player's Autoplay switch (`"false"` when off); also Settings → Playback → Autoplay |
| `'deeni-feed-playback'` | Settings → "Playback in feeds" (`false` turns off inline playback in cards; `lib/feed-playback.ts`) |
| `'deeni-watch-progress'` | How far each video was watched, `{ [youtubeId]: { t, d, at } }` (`lib/watch-progress.ts`, at most 300) |

`hooks/useWatchLater.ts`, `hooks/useLikedVideos.ts` (both via `hooks/useSavedList.ts`), `hooks/useWatchHistory.ts` and `hooks/usePlaylists.ts` are built on `lib/local-store.ts` (`createLocalStore` + `useSyncExternalStore`), so every component shares one copy of the data and writes never use stale state. Use these hooks rather than reading/writing these keys directly. The "Watch Later" (`pl-watch-later`) and "Liked Videos" (`pl-liked-videos`) playlists are derived from their stores, not stored separately. Pages refer to the same video by internal id (`"v3"`) or YouTube id; `lib/media-lookup.ts` resolves both, and the hooks store canonical ids. `lib/language-prefs.ts` merges into `deeni-lang-prefs` without changing `isGuest`.

**Watched progress** (`lib/watch-progress.ts`), as on YouTube: the watch player saves how far a video got (every 5s while playing, and on pause, the end, leaving the video or hiding the tab; reports from before its resume seek are skipped so they can't wipe the place), and so does a card's inline playback. Every video thumbnail shows it as `<WatchedBar videoId>` (`components/watched-bar.tsx`: a 4px red bar along the bottom edge, inside the thumbnail's box, next to the duration; cards, History, related list, search, Watch Later, Liked, playlist panel, scholar page). Opening a video (from History or anywhere) goes on from that place (`resumeTime`: after a card's preview its exact time wins); under 5s, or a video watched to its last 10s (3% for long ones), counts as not started / finished: a finished one shows a full bar and starts again. Inline playback starts where the video was left (`start=` in its URL) and adds the video to History once it has played 5 seconds. Shorts have no progress.

### Shorts page (`app/shorts/page.tsx`)

The most complex file (~1800 lines), entirely `"use client"`. Key mechanics:

- **Opening a short from a link** (`/shorts?v=ID`): the starting index comes from the URL in the first render and the feed scrolls there before paint, so only that short's player loads (no jump from the first short)
- **Scroll container**: `position: fixed` (phones: from the top down to the bottom nav; desktop: below the header) with `overflow-y-scroll overflow-x-hidden touch-pan-y snap-y snap-mandatory`. It only moves up and down: the hidden action rails of the other shorts slide in from the right and must not make it pannable sideways. `AppShell` gives `/shorts` no padding or minimum height, so the page behind the feed never scrolls.
- **Each section**: `h-full` of the feed on phones, `h-[calc(100%-32px)]` on desktop (the next video peeks at the bottom); the video keeps a 9:16 aspect on desktop. Don't size sections with `100vh`: on phones it is taller than the visible screen while the browser bar shows, so shorts stop fitting the screen.
- **Title and channel** (bottom left): on phones the space under the title, above the progress bar, grows with the screen like the YouTube app's (`clamp(24px, 5svh, 44px)`); 24px from the bottom on desktop.
- **Action rail**: from `lg` up, like/comment/share/save/report sit beside the video as `bg-secondary` circles with `text-foreground` icons (readable in light mode); below `lg` they sit over the video, white on a dark backing, and their size (34-48px), gaps and bottom offset follow the screen's height (`svh` clamps), so the column fits between the top controls and the title on any phone, also an iPhone SE in Safari with its toolbars (it used to reach up under the ⋮)
- **Mobile iframe cover**: `.shorts-player-box` is a size container and `.shorts-video-iframe` (and the cover, `.shorts-poster`) is `max(100cqw, 100cqh*9/16)` × `max(100cqh, 100cqw*16/9)`, centred (browsers without container query units, e.g. Safari 15 on iPhone 7/6s/SE, get the same size from the screen: `100vw` and `100dvh - 56px - safe area`; keep it pure CSS, so the server's HTML is right before any script runs), so the 9:16 player covers the box (cropping the overflow) with no black bars at the sides. Most phones are wider than 9:16 once the bottom nav is counted. Until its video plays, a short shows its cover (`ShortCover`): the video's first frame, YouTube's `frame0.jpg` (about 270×480; 480×480 for a square video), `object-contain` in the same 9:16 box as the video (`.shorts-poster`), so the picture doesn't change when the video starts, as in YouTube's apps and KinTube (`hbg/safekids-*`: `ShortsCover`). Without a first frame (an error or YouTube's 120×90 placeholder) it's the thumbnail. YouTube's 4:3 thumbnails, often with black strips at both sides, used to show the short smaller than its video, which then seemed to zoom in.
- **Players (instant switching, no black screen)**: the active short and its neighbours (`PRELOAD_RANGE`) have a mounted iframe. Neighbours mount 1.5s after the first short starts playing, when the browser is idle (or after 6s). Each iframe's `src` is fixed (`autoplay=0`) and never rewritten; play/pause/seek/mute go through postMessage. The next short is "primed": played muted under its thumbnail, then paused at 0, so its stream is buffered. Each short's thumbnail covers its iframe, and the iframe stays `opacity-0`, until that player reports `playerState === 1`. Keep the opacity: YouTube resizes its `<video>` while loading, which Lighthouse otherwise counts as layout shift for the page (CLS went 0.94 → 0).
- **iPhone, iPad and Safari** (`hosted`, as on the watch page): no short has a frame of its own. The shared player is attached to the short on screen (`attachHost(box, "short")`: fixed to the screen, the 9:16 video covering the box with no side bars, YouTube's bars cropped off in 120px bands above and below; it follows the feed while it scrolls) and each new short goes into it with `loadVideoById`, so the sound a tap gave it stays on while swiping (YouTube's own apps also reuse one player). The frame sits under the feed (`z-[2]`; black behind it on phones); the short's section and box turn see-through once it plays, and the frame stays hidden (`setHostVisible`) until then, behind the thumbnail. On phones a tap on a Shorts link already lays it out (invisible) over the whole screen above the bottom nav, so YouTube redraws it at that size while the page loads. It is shown with `revealHost` only once its size has been the same for 400ms (YouTube redraws its video a moment after its frame changes size or comes out of `display: none`; shown at once, a short appeared small and then zoomed to fill the screen); the watch player hides its thumbnail the same way. Messages about another video are ignored; on attach the page takes the state YouTube already reported (`hostInfo()`), since a tap may have started the short before the page existed. No automatic mute by the play watchdog here.
- **Autoplay and sound**: browsers allow sound only after a click, tap or key press on the page (wheel scrolling and swipes don't count). Each player is asked for YouTube's `onAutoplayBlocked` event (`addEventListener` command); when it fires for the active short, the short plays muted at once and a "Tap to unmute" pill shows. That automatic mute (`autoMuted`, not the visitor's choice) is undone by their next click or key press anywhere; a tap on the video then unmutes instead of pausing. Don't mute on a timer: slow-loading shorts were treated as blocked and everything after stayed muted.
- **Play watchdog**: after a switch, `startPlayer` checks every second (5 times) that the active player really plays and resends `playVideo` if not (commands can get lost while a player loads or seeks), muting only as a last resort. The UI shows "paused" only for a real pause after the short has played (`activePlayedRef`), not for the passing states while switching.
- **Taps**: a tap within 250ms of a scroll (stopping a swipe) doesn't toggle play/pause; tapping a short that isn't active (the next one peeking in on desktop) scrolls to it.
- **Scroll detection**: `scrollend` event (Chrome/Firefox) with a 250ms debounced fallback; arrow keys and the up/down buttons switch immediately
- **Controls visibility**: gated on `isActive && !isScrolling` for the current video; `(isHovered || isActive) && !isScrolling` for top controls
- **YouTube postMessage protocol**: iframes use `enablejsapi=1`. After an iframe loads, `{ event: 'listening', id }` is sent repeatedly until the player answers. Incoming messages are matched to the iframe that sent them (`e.source`), so only the active player drives the progress bar and play state. YouTube sends periodic `infoDelivery` messages (`currentTime`, `duration`, `playerState`). Commands are `{ event: 'command', func, args }` (`playVideo`, `pauseVideo`, `seekTo`, `mute`, …). All postMessage calls target `'https://www.youtube.com'`.
- **Progress bar**: `absolute bottom-0` inside the video container, 3px tall, red fill. `videoCurrentTime`/`videoDuration` state is reset to 0 on every video switch. `videoDurationRef` (a ref mirroring `videoDuration`) is used inside mouse/touch drag closures to avoid stale state captures. Drag-to-seek wires `mousemove`/`mouseup` on `window` and `touchmove` on the bar element.

### Bottom of the screen on phones

`MobileNav` follows Chrome's edge-to-edge guide (Chrome 135+ with `viewport-fit=cover` draws under the phone's navigation bar): `--sab-max` (`app/globals.css`) is `env(safe-area-max-inset-bottom)` (falling back to the current `safe-area-inset-bottom`); the nav is `56px + --sab-max` tall with that as padding and `bottom: calc(env(safe-area-inset-bottom) - --sab-max)`, so it always sits right above the gesture bar / Back-Home-Recents buttons / home indicator without relayout. Don't put the plain inset in `padding-bottom` (layout thrash while Chrome's bottom bar moves). `AppShell`'s bottom padding uses `56px + --sab-max`. While shown, the nav sets `data-bottom-nav` on `<html>`; toasts (`Toaster` in `app/layout.tsx`) use `--toast-bottom`, defined on the toaster element (not `:root`: changing a custom property on `:root` restyles the whole page, ~100ms TBT on the home feed): 16px above the nav when it's there, 16px above the bottom edge (plus the inset) on pages without it, 30px on desktop (YouTube's).

`app/contexts/header-context.tsx` provides `{ headerVisible, setHeaderVisible }` — used by the Shorts page to auto-hide the header and by `AppHeader`/`DesktopSidebar` to slide up/down.

### Theming

CSS custom properties defined in `app/globals.css` for all colour tokens (`--background`, `--foreground`, `--primary`, etc.), using a YouTube-like neutral palette (see "UI conventions"). ### Header clearance rules

The `AppHeader` is `fixed top-0 h-14 z-40` (56px). Every page must push its content below the header. There are two patterns:

**Standard pages** — add `mt-14 md:mt-16` to the outermost content wrapper. This applies to all pages except video/playlist detail.

**Video & playlist detail pages** (`/videos/*`, `/playlists/*`) — these have a `sticky` back button bar that must stack on top of the content below the header:
- Add `pt-14` to the outermost `<div>` wrapper (not `mt-14`)
- The sticky back button uses `sticky top-14 z-10` (same 56px)
- The mobile video element directly below the back button must have **no** extra top padding — `pt-14` on the wrapper already handles clearance
- Desktop inner content divs must have no `pt-*` top padding (it stacks naturally)

The math: header occupies 0–56px. With `pt-14`, content starts at 56px. The `sticky top-14` back button sticks at exactly 56px, immediately below the header. The video below the back button starts at 56px + back-button height (~40px) = 96px, with no gap.

### VideoCard and VideoGrid

`components/video-card.tsx` follows YouTube's card: rounded thumbnail, 36px channel avatar, 16px title (2 lines), 14px channel and views lines, no card border or shadow. Two render paths, gated on `isHorizontal`:
- `isHorizontal={false}` (default): grid card.
- `isHorizontal={true}`: phone list item, with an edge-to-edge thumbnail and "channel · views · time" on one line.

**Inline playback** (YouTube's "Playback in feeds"): `InlinePreview` (`components/inline-preview.tsx`) wraps the thumbnail link of both card variants and of search results, and the video plays in the thumbnail, muted (the nocookie embed with the watch player's `CROP` trick; YouTube's centre play/pause icon still shows for its first seconds, which is accepted). Opening the card then starts the watch page where the preview was (`takePreviewResume`). One player at a time; none while the tab is hidden; Settings → Playback in feeds turns it all off.
- Mouse (youtube.com, measured): starts after resting 300ms on the thumbnail. The volume button is YouTube's plain white icon (a dark circle on hover). The progress bar is a 5px line on the bottom edge; hovering it lifts it 10px with its ends 12px in, darkens the bottom and shows the 12px playhead (16px dragging) and the storyboard; click or drag seeks (a full seek on release; without a storyboard the video follows the drag).
- Touch (YouTube app / m.youtube.com): once scrolling stops, the card nearest the middle of the screen (thumbnail ≥75% visible, ≥240px wide) plays; it stops at <50% visible. Touch and hold a card (a 500ms long press, no scroll) plays it, keeps it until the next scroll, and lifting the finger doesn't open the video; anything shorter is a tap and opens the video (250ms caught slow taps, which then needed a second tap). The bar is a 3px line flush with the card's bottom edge with the playhead always on it, straddling the edge; drag sideways to seek (a tap on it opens the video like the rest of the card), while vertical swipes still scroll (`touch-pan-y`). No autoplay with data saver on.
- Kept light (Lighthouse mobile): cards render the same on the server and in the browser (mode and setting are read in effects/handlers, not hooks), a mounting card only joins a page-level list, the player is a separate chunk (`components/inline-preview-player.tsx`, loaded with a plain `import()`), and on touch screens nothing plays until the first scroll or touch, or 5s after load (2.5s let Lighthouse catch the player chunk). The wrapper still costs about +60ms TBT on the mobile home page (≈615 → 675ms median of 8 runs; LCP, CLS and desktop unchanged).

`components/video-grid.tsx` renders a list of `VideoItem`s as the standard grid (md+) plus the phone list, with only the first card loading early. Use it for video lists instead of hand-written cards (category, scholar and channel pages already do). The home feed has its own grid: 3 columns with the full sidebar and 4 with the mini sidebar (at xl+; 3/2 on narrower screens).

`components/short-card.tsx` is the one Shorts card (9:16 thumbnail, title, views, menu) used on the channel, scholar, History, Watch Later and Liked pages. On the video page the related list's thumbnails are 46% of the side column (168–236px wide), using the 480px image. Beside the player (from 1016px) that column is sticky under the header (`top-20`), at most the screen's height (`100vh - 104px`), and scrolls on its own with `yt-scrollbar`, so the page itself only scrolls as far as the description. Card and list-row text is the same everywhere: titles 16px medium on desktop / 15px on phones (`text-[15px] md:text-base`), secondary text 14px / 13px; the compact related list and playlist panel use the phone sizes.

### UI conventions (YouTube-like)

- Font: Roboto via `next/font` (`--font-roboto`, Tailwind `font-sans`). Bangla/Arabic/Urdu text falls back to the system font.
- Colours: the tokens in `app/globals.css` use YouTube's neutrals (`muted` = #f2f2f2 / #272727 fills and chips, `accent` = hover, `muted-foreground` = #606060 / #aaa secondary text). YouTube blue (`#065fd4`, dark `#3ea6ff`) is only for the Sign in button, the search focus border and links inside descriptions.
- Three-dot menus: use `MoreButton` (`components/more-button.tsx`): solid dots (`MoreVertIcon`), 20px on phones and 24px from `md` up, in a 40px circle, always visible on cards and rows. Don't use lucide's `MoreVertical` (its dots are too small).
- Nothing stays behind after a click. Focus rings and outlines show only while the visitor uses Tab: a script in `app/layout.tsx` sets `html[data-keyboard]` on Tab and removes it on any click or touch, and `app/globals.css` hides rings (`ring-*`) and outlines without it (`:focus-visible` isn't enough: a closing menu or dialog gives focus back to its button, which browsers then outline). Text fields show focus with their border colour. For anything else that focus must not leave behind after a click, use the `kb:` variant (`kb:group-focus-within:opacity-100`), not plain `focus-within`/`focus-visible`. `hover:` applies only where there is a mouse (`hoverOnlyWhenSupported`), so a tapped button keeps no hover colour on phones; give it an `active:` state instead.
- Menus (`components/ui/dropdown-menu.tsx`) don't lock the page: it, and any list in it such as the related videos, scrolls while a menu is open, and scrolling closes the menu (`hooks/use-menu-dismiss.ts`, also used by the Shorts page's own ⋮ menu). A click outside only closes it; it doesn't also open the video under the pointer. (YouTube blocks scrolling while a 3-dot menu is open; this is friendlier.) Popups of the fixed header pass `closeOnScroll={false}`. Dialogs and bottom sheets still lock the page.
- Messages at the bottom: only through `notify(message, undo?)` in `lib/notify.ts`, never sonner's `toast` directly. Show one when the result is somewhere else (saved to Watch later or a playlist, link copied, report sent), when something was removed or hidden (with Undo: the hooks' remove functions return it), or when something failed. None when the page shows the result itself: switches, ticks, theme, a comment or playlist that appears, a filled Like button, a thank-you screen. "Not interested" and a hidden notification say so in place, with Undo. Form mistakes show at the field or keep the button disabled. One line, one at a time, sentence case, no "!". The message is a card (`components/message-card.tsx`) at the bottom left as on YouTube (16px in, 30px up; on phones above the nav, full width), dark on a light page and the other way round; about a video it carries its picture (`thumb: mediaThumb(id)`), and "Saved to ..." offers Change.
- Share and Save icons: `ShareIcon` (YouTube's curved arrow) and `SaveIcon` (its bookmark, `filled` once saved) from `components/icons/action-icons.tsx`, everywhere; not lucide's. The Save button's bookmark is filled when the video is in any playlist (`usePlaylists().isSaved`).
- Saving to Watch later: `useWatchLater().toggleWatchLater(video)` (it shows the message); menus say "Save to Watch later" / "Remove from Watch later".
- A menu item that opens a dialog uses `<DropdownMenuItem afterClose={() => setOpen(true)}>`: the menu closes, focus returns to its button, then the dialog opens. Don't `preventDefault` in `onSelect` for this: it leaves the menu open under the dialog.
- Hover-only controls, as on YouTube: the compact lists beside the player (video page related list, playlist panel) use `MoreButton size="sm"` (20px dots, 36px circle), shown on row hover, while its menu is open, or while the row has keyboard focus (`kb:`). History's remove ✕ is desktop-only and shown on row hover; on phones "Remove from History" is in the ⋮ menu. Always hide with the `can-hover:` variant (`can-hover:opacity-0 can-hover:group-hover:opacity-100`, defined in `tailwind.config.ts`), so touch screens, which can't hover, still show the control.
- Descriptions (videos, shorts, channel/scholar About): render with `DescriptionText` (`components/description-text.tsx`). It keeps line breaks, wraps long links with `overflow-wrap: anywhere` so they never run off the screen, and turns URLs and #hashtags into links. On phones the video and playlist pages open the full description as a bottom sheet (`Drawer`).
- Sizes: page titles 24px bold, card/list titles 16px medium (14–15px on phones), secondary text 12–14px. Avoid text under 12px except the 10px nav labels.
- Sidebar (`components/sidebar-expanded-content.tsx`), as YouTube's guide: entries Roboto 14px/20px (500 for the current page), 24px icons with a 1.5px line (2px for the current page); section headings 16px/22px medium, and "You ›" is a link row to the You page; a footer of 13px medium grey links and a 12px copyright. Popup and panel titles (e.g. "Notifications") are 16px medium, like their section headings.
- Chips: `h-8 px-3 rounded-lg text-sm font-medium`, `bg-muted hover:bg-accent`, selected `bg-foreground text-background`.
- Dropdown menus (`components/ui/dropdown-menu.tsx`) have YouTube-sized rows: 36px+, 20px icons (the item sets the size and gap; don't add `mr-*` to icons), full-width hover.
- Account menu (`components/account-dropdown.tsx`): profile header with "View your account", then grouped rows; Appearance opens as an in-place sub-page with a back arrow (same on phones).
- Notifications panel (`components/notification-dropdown.tsx`): the list area has a fixed height from the first frame and the loading placeholders fill it, so the panel opens at full size instead of growing after loading.
- Scrollable sidebars, popups and panels use `yt-scrollbar` (`app/globals.css`): thin, no arrows, transparent track, grey thumb while hovered.
- Save card (`components/save-card.tsx`), YouTube's "Save to...": open it with `openSaveCard(video, button?)` (`lib/save-card.ts`) from anywhere; one card for the whole app (`SaveCardHost` in the layout, its code loaded on first open). It opens at the button pressed (after a menu: at its 3 dots; left edges in line), a bottom sheet on phones: a row per playlist (cover, name, privacy, a bookmark filled once saved; Liked videos isn't listed) and "New playlist", whose form opens in the card. As on YouTube since 2026, a choice saves or removes and closes it, and the message offers Change (opens it again) or Undo. Scrolling closes it, as every menu. Playlist forms use `PlaylistNameField` and `PrivacySelect` (`components/playlist-fields.tsx`), not a native `<select>`. Other selects (e.g. the You page's default language) use the same file's `OptionSelect`: an outlined field with a small label and chevron, opening a menu with an optional icon and second line per choice and a check mark.
- History rows follow YouTube's (measured): title 18px/26px regular on desktop, 14px/20px on phones; "channel · views" and the time 12px grey. The whole text block, channel name included, opens the video. Horizontal rows (Shorts on History, the home chip bar) must not set `touch-action: pan-x`: a vertical swipe starting on them has to scroll the page.
- Settings → Language & content lists the languages as checkbox rows in the page (no pop-up to scroll; at least one stays ticked). Settings → Playback has "Playback in feeds" and "Autoplay".
- `/channels`: each channel has a grey "On Home ▾" / "Hidden ▾" pill (like YouTube's "Subscribed ▾"; no blue switch) that opens a menu with "Show on Home" and "Hide from Home", each with a line saying what it does (`feed-visible-channels`, the same list as "Don't recommend channel"). Hiding removes the channel's videos from Home only and dims its avatar. The header counts the channels on Home with "Show all"; a "Hidden N" chip filters them; hiding shows a message with Undo, showing again none. Under 360px the pill shows only its icon; the title and search sit side by side from `lg`.
- No underlines: links and text buttons don't underline on hover (on phones the hover state sticks after a tap). The channel/scholar tabs keep their active underline; their hover line is mouse-only (`can-hover:`).
- Voice search (`components/voice-search.tsx`): the mic in the desktop header and in the phone search screen opens a listening dialog (browser Web Speech API, English or Bangla) and searches what was said. Its z-index is above the phone search screen (z-60).
- Dialog widths: the `max-width: 100vw` guard on `[class*="fixed"]`/`[class*="absolute"]` in `app/globals.css` lives in `@layer base` so `max-w-*` utilities win. Unlayered, it made every dialog full-width on desktop.

### Route patterns

- `/` — home feed
- `/videos/[slug]/[id]` — video detail (no desktop sidebar, full-width player). The address is `/videos/<title in Latin letters>/<YouTube id>`, e.g. `/videos/islamic-halaka-shesh-jamanar-fitna-prof-dr-mohammad-monzur-e/XVscS6piz9A`: readable and clean to share (no `%20` or `%E0%A6…`). Always build links with `videoPath(video)` / `videoPathForId(id)` from `lib/video-url.ts` (the slug comes from `slugify` in `lib/slug.ts`, which writes Bangla in Latin letters). Only the id finds the video; the layout permanently redirects any other slug or the internal id (`/videos/x/v2`, old channel-name links) to the readable address, and sets it as the canonical URL
- `/playlists/[slug]/[id]` — playlist detail (no desktop sidebar)
- `/shorts` — vertical shorts feed (fullscreen, header auto-hides)
- `/channels/[slug]`, `/scholars/[slug]`, `/categories/[slug]` — entity detail pages. Both scholar routes render `app/scholars/[slug]/scholar-view.tsx`, which shows the profile or the About page from the URL; the About tab switches with `window.history.pushState` (Next.js syncs it with `usePathname`), so the About page opens instantly with no request, even in dev
- `/signin` — auth page (no desktop sidebar)
- `/you`, `/history`, `/liked-videos`, `/watch-later` — account/activity pages
- `/more`, `/settings`, `/help` — utility pages (each has sub-pages under the same prefix)
- `/donate`, `/search`, `/playlists` — standalone pages

### Page titles and 404s

Pages are client components, so they can't export `metadata`. Each route has a small server `layout.tsx` that sets the title (the root layout adds the `"%s - Deeni.tube"` template). The `[slug]`/`[id]` layouts for channels, scholars, categories and videos also call `notFound()` for unknown ids, which renders `app/not-found.tsx`. Unknown ids return a real 404. These layouts also export `generateStaticParams`, so every video, scholar (and About), channel and category page is pre-rendered at build time: `<Link>`s prefetch them in full and clicks open them without a server round trip (other URLs, such as `/videos/x/v2`, still render on demand). Don't add an `app/loading.tsx` (or a `loading.tsx` above these layouts): it starts streaming before the check, which turns the 404 into a 200. `/search` and `/shorts` wrap their content in `<Suspense>` because they call `useSearchParams()`. The favicon is `app/icon.png` (cropped from the logo).

### Image loading (measured with Lighthouse, mobile + desktop)

- Load **only one** image per page early: the main (LCP) image, via `imagePriorityProps(...)` / `priorityForIndex(index)` from `lib/image-priority.ts`. Loading several images early made LCP worse on mobile: they compete for bandwidth, and pages that render a hidden desktop/mobile copy of a list download the hidden copy's eager images too.
- Default is `preload` + high priority (React starts the download during render, which helped the heavy client-rendered lists). Watch Later and Liked measured better with `{ preload: false }` (eager + high priority). Don't add early loading to the video page's related list; it measured no better. On the watch pages the main image is the player's thumbnail (preloaded). Video and short cards call `warmYouTube()` (`lib/warm-youtube.ts`) on hover/touch to preconnect to YouTube before the click. On Shorts only the first short's cover (its first frame) loads early (it is the main image until the player starts; mobile LCP 2.6s → 2.3s).
- `youtubeThumb(id, "small")` (320 px) is only for images up to ~170 CSS px wide where the page has no hidden duplicate using the larger size; otherwise use the default 480 px version so both copies share one download.
- The header logo uses `public/logo-header*.webp` (sized for the header); the original PNGs are kept for other uses.
