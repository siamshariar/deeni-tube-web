This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # start dev server (localhost:3000)
npm run build    # production build
npm run lint     # ESLint (must pass with 0 problems)
npm run start    # serve production build
npm run og       # make the share cards (public/og) and app icons, after adding a channel, scholar or category
npm run storyboards   # fetch YouTube storyboards, thumbnail colours, caption languages and shorts' shapes for added videos and shorts
```

**E2E tests** use Playwright:
```bash
npx playwright install chromium   # first time only
npx playwright test               # run all tests (starts dev server automatically)
npx playwright test e2e/navigation.spec.ts --project=chromium  # single file
```

## Stack

- **Next.js 16** (App Router, Turbopack for `dev` and `build`), **React 19**, **TypeScript**, **Tailwind CSS v3**
- Server `layout.tsx` files must `await params` (Next 16 removed synchronous access); client pages use `useParams()`/`useSearchParams()`
- `next/image`: use the `preload` prop (`priority` is deprecated in Next 16)
- **shadcn/ui** (Radix UI primitives) — components live in `components/ui/`
- **lucide-react** for icons, **next-themes** for dark/light mode, **sonner** for toasts
- No backend, no API routes, no database — all data is static mock data

## Architecture

### Layout shell

`app/layout.tsx` composes the full shell in this order:

```
HeaderProvider
  AppHeader          (fixed top, 56px, z-40)
  DesktopSidebar     (fixed left, 240px/72px, z-30, hidden on video/playlist/signin pages)
  AppShell           (<main> that offsets left-padding to match sidebar width)
    {children}
  MobileNav          (fixed bottom bar, mobile only, hidden on detail/fullscreen pages; stays put while scrolling)
```

**AppShell** (`components/app-shell.tsx`) dynamically sets `md:pl-[240px]` or `md:pl-[72px]` on `<main>` by reading sidebar width from `window.__sidebarGetState`. The desktop sidebar and AppShell both listen to the custom `"sidebar-state-change"` window event to stay in sync.

### Sidebar communication (global window pattern)

The desktop sidebar exposes two globals set in a `useEffect`:

- `window.__sidebarToggle()` — toggles collapsed state; called only by the hamburger in `AppHeader`
- `window.__sidebarGetState()` — returns current `isCollapsed` boolean

Sidebar state is persisted to `localStorage` key `'sidebar-collapsed'`. The sidebar reads this on mount to restore state across navigations. The header hamburger button toggles the desktop sidebar on pages that have one. On `/videos/*` and `/playlists/*` there is no sidebar (as on YouTube): the hamburger opens the menu over the whole window (`DesktopSidebar`, a Radix dialog; YouTube's, measured): 240px, also over the header, with the menu button and the logo where the header has them, half black behind it, 0.2s, no border; the page is locked, the video goes on, and Escape, a click beside it, its button or a link close it. Rows are 204x40px, 12px from the left; the mini sidebar's tiles 64x76px. `/signin` has no global header, sidebar or bottom nav. A script in `app/layout.tsx` applies the saved collapsed state before first paint (see the "Sidebar first paint" block in `app/globals.css`).

### Data layer

All data is static TypeScript arrays in `lib/`:

| File | Contents |
|---|---|
| `lib/video-data.ts` | `VideoItem[]` — main feed videos with YouTube video IDs. `duration` is the video's real length on YouTube (`"lengthSeconds"` on its watch page), so the card matches the player; the saved-list and history hooks take it from here, not from copies saved earlier |
| `lib/shorts-data.ts` | Every short, once: the Shorts page, channel and scholar pages, History, Liked, Watch later and playlists all read it (`shortsOfChannel`) |
| `lib/mock-data.ts` | Channels and scholars for listing pages |
| `lib/channel-data.ts` | Sidebar channel list |
| `lib/scholar-data.ts` | Sidebar scholar list |
| `lib/playlist-data.ts` | Static playlist definitions |
| `lib/storyboard-data.ts` | Each video's YouTube storyboard; generated by `npm run storyboards` (`scripts/storyboards.mjs`), don't edit |
| `lib/thumb-tints.ts` | Each thumbnail's main colour (a related row's hover colour); generated by the same script, don't edit |
| `lib/caption-data.ts` | Which captions each video and short has on YouTube; generated by the same script, don't edit. A video that isn't 16:9 has a `ratio` in `lib/video-data.ts` |
| `lib/short-ratios.ts` | The shorts that aren't 9:16 (square ones), where captions are drawn goes by it; generated by the same script, don't edit |

All videos are YouTube embeds using `<iframe src="https://www.youtube.com/embed/{videoId}?...">`. On the Shorts page, iframes include `enablejsapi=1` and are controlled via the YouTube postMessage protocol (see Shorts page section below). The watch pages (video, playlist) use `components/youtube-player.tsx`: YouTube's privacy-enhanced embed (`www.youtube-nocookie.com`, which leaves out creators' end-screen cards, the video thumbnails the normal embed shows over a video's last seconds; same postMessage API, so the origin checks use that host) with **our own YouTube-style controls**. Shorts still use `www.youtube.com`. YouTube shows its suggestions (the "More videos" pill, share button, title bar) whenever the embed is paused and for a few seconds after playback starts, so: YouTube's controls are off (`controls=0`); a transparent layer over the frame takes every click and hover; and the frame is `CROP` (120px) taller than the box at the top and bottom, which cuts those edge overlays off while the video still fills the 16:9 box exactly. The frame is always cropped, also with captions on (see Captions below). A video narrower than 16:9 (`ratio`) gets a frame as wide as the video, or the crop would cut into it. Our controls are YouTube's updated ones (measured on youtube.com and m.youtube.com): each group on its own rounded `bg-black/30` backing, no gradient. With a mouse (`can-hover:`): a 56px row of 40px groups, 12px in and 8px up: play, alone in its circle (a single video has no Next on youtube.com, also not in full screen; in a playlist Previous and Next share a pill 8px after it, 52px each); volume (its 52px slider opens on hover); the time (a click switches to the time left); then Autoplay, captions, settings, theater mode and full screen in one group (`BarButton`: an inner highlight, and its name and key above the bar on hover). On touch screens: previous, play (56px) and next in the middle, previous dimmed on the first video (`hooks/use-video-trail.ts`), Autoplay, captions and settings in a group at the top right, the time and full screen above the bar, whose line is 22px from the bottom; no volume button (phones have keys). Plus a seekable progress bar with storyboards (see below), a settings menu (Autoplay, Ambient mode, Subtitles/CC with the languages and Auto-translate, sleep timer (`lib/sleep-timer.ts`: it runs outside the player, so one that ends on a page without a video doesn't stop the next one), speed; a press anywhere else or Escape closes it, on the video without pausing it; quality can't be set through YouTube's embed; it scrolls when the player is too short for it) and full screen (the whole page goes full screen and the player fills it, `fixed inset-0`, so it goes on with the next video, whose page has its own player; `keepFull` hands it over, `html[data-player-full]` hides the page's scrollbar; iPhone, which has no full screen for pages, just fills the window; on screens wider than 16:9 the frame is no wider than the video, or the crop would cut into it), plus YouTube's keys (space/k, j/l, ←/→, f, m, c, Shift+N, Shift+P). The thumbnail covers the player (`opacity-0`, for the same layout-shift reason as Shorts) until it plays; the handshake starts on mount as well as on load, because the server-rendered frame can load before React hydrates. Playback starts with `playVideo`; if YouTube reports `onAutoplayBlocked` it plays muted with a "Click to unmute" button. At the end our end screen covers YouTube's: "Up next in N" (YouTube's 8s countdown, 3s in full screen, down to 1; Cancel, Play now) when Autoplay is on, else Replay and the "Up next" card. The controls stay over it, as on YouTube (on phones the switches at the top right), so Autoplay can be switched on there, which starts the countdown. **Nothing stays stuck** (`watchPlayback`, as on Shorts): until the video plays it is asked again each second (commands get lost while a player loads or seeks, which left the next video just sitting there), muted if Safari left it paused, loaded again once after 10s (a new iframe `key`, or `hostLoad(…, true, true)`; going on from where it was), and 15s later "This video isn't playing" with Try again and Next video; twice as long while loading; a stream that broke off in the middle is loaded again after 5s. Stuck 8s within its last 10 seconds (YouTube's stream often breaks off after a jump to the end) counts as finished (`finish`), so the next one plays. YouTube's `onError`: "This video isn't available"; if Autoplay brought it there, the countdown to the next one follows, at most 3 in a row. On touch screens the controls hide 3s after playback starts or after a tap (2.5s after the last mouse move with a mouse); only a mouse over the control bar keeps them up.

**Theater mode** (`lib/theater.ts`, "Theater mode" in `app/globals.css`), YouTube's, measured: with a mouse from 768px; the player over the whole width right under the header, `min(56.25vw, 100vh - 169px)` high and at least 480px, the title 12px and the side column 24px under it. CSS only, keyed on `html[data-theater]` (set before first paint), through the `watch-page`, `watch-top`, `watch-frame`, `watch-box`, `watch-side` and `watch-video` classes: the player's element never moves in the page, or its frame would reload. The change is a view transition where the browser has them (`view-transition-name` only during it: a named element can't fill the screen over the header). The header over it is dark in the light theme too (`.app-bar` gets `dark`; a script in `app/layout.tsx` does that before first paint).

**Ambient mode** (`components/ambient-light.tsx`, `lib/ambient.ts`, "Ambient mode" in `app/globals.css`), YouTube's, measured: with a mouse, in the dark theme around the player (a 110x75 canvas with the storyboard's 80x45 frame blurred 5px at 40%, stretched to 1.5 × 2 of the player; each new frame fades in over 5s), and in theater mode at the video's sides in both themes (twice the video; one flat colour at 24% in the light theme). Around the player it is behind the page (`z-index: -1`, the page itself see-through and clipped, so the glow doesn't make it longer; no stacking context on the way, or Safari's shared player would cover the controls) and under the header, which fills in over the first 28px of scrolling. Its switch is in the player's settings.

**iPhone, iPad and Safari: one shared player** (`lib/player-host.ts`, following Quran Tube, which was tested on real iPhones). WebKit only allows sound when a player that is already playing is unmuted inside the tap; a watch page's own new frame loads after the tap, so it would play muted with "Tap to unmute". So on those browsers (detected by user agent, `hostWanted()`; Chrome/Android/Firefox keep the page's own frame) one frame, created outside React at the end of `<body>` soon after load (`bootPlayerHost()` in `AppShell`), plays a muted placeholder video (`p3Mrisem6ek`, Deeni Info Tech) while hidden. A window click listener catches taps on any link to `/videos/<slug>/<id>`, `/shorts?v=<id>` or `/shorts` (its first short, `FIRST_SHORT_ID`; not on the Shorts page itself), or an element with `data-play-id`, and, inside the tap, sends `loadVideoById({ videoId })` (no `startSeconds`: it broke the swap on iPhones) → `unMute` → `playVideo`, then re-sends `unMute` for a few seconds if YouTube reports muted again. The watch player (`hosted` mode) renders no frame of its own: it attaches the shared frame, which is placed over its box in page coordinates (z-index 1, under the player root's own layer, `z-[2]` with a transparent background), and its controls drive it; the end screen's Next/Play now/Up next also go through `playFromTap`. Messages about another video (`videoData.video_id`) are ignored, so the placeholder never shows. Full screen fills the window (and asks for the whole page's full screen where possible), since the frame isn't inside the player element. When no watch page uses it, the frame hides, pauses, and goes back to the muted placeholder after 1.5s. Opened directly from a link (no tap in the app), the video still plays muted with "Tap to unmute"; that tap gives the shared player sound for the rest of the visit (`hostSoundAllowed()`; until then pages must not ask it for sound, which Safari answers by stopping the video). The Shorts page uses the same frame (see below). The video page's Autoplay switch is saved per device (`'deeni-autoplay'`); the playlist page passes its own (`autoplay`/`onAutoplayChange`) and moves on at once. On the video page "Up next" is the next video in catalogue order (the related list is rotated to start there). Their layout comes from `components/watch-layout.ts` (YouTube's, measured again on Nov 23, 2026, and equal to it at 900–2560px wide windows: 16px at the sides and between the columns, 12px under the header; two columns from 1016px; a side column of 27.5% of the window, 320–700px; one column below 1016px). One difference on purpose: in a low window the 16:9 player's height stops at `100vh - 176px` (YouTube's at `100vh - 116px`), so the title and channel show without scrolling; the side column then takes the spare width, up to 35% of the window (700px at most), so there's no empty space at the sides. The player is never under 640px wide. `<body>` uses `overflow-x: clip` (not `hidden`, which makes body a scroll container and silently breaks every `position: sticky`), and `app/globals.css` also keeps it that way while Radix menus/dialogs lock scrolling (`html body[data-scroll-locked]` overrides the lock's `overflow: hidden` and scrollbar `margin-right`, which made the related column jump and the page shift; the lock still blocks wheel/touch scrolling). The player box is always exactly `aspect-video` with no max-height, so YouTube never adds black side bars; on the video page it is one element placed with CSS (edge to edge on phones), not a JS phone/desktop switch, so the server HTML already shows it.

**Storyboards** (`lib/storyboard.ts`, `components/storyboard.tsx`): the frames YouTube shows while a progress bar is hovered or dragged, on the watch player and in playing cards. YouTube's sheets need a signed link from the video's watch page, so `npm run storyboards` fetches them into `lib/storyboard-data.ts` (run it after adding videos; the links don't expire: they are made once, when the video is processed, and come out the same every time). Nothing loads before the bar is used (or a related row hovered, see Related videos): then the data file (its own chunk) and the video's L0 sheet (25 KB, 100 tiny frames of the whole video), which shows at once under the sharper sheet. A video without one, or whose sheets can't load, shows just the time. All sizes were measured on youtube.com: the watch page's bar is 4px (6px under the pointer), 12px in from the sides and 56px above the bottom, its playhead 12px (20px); the box is a 240px frame in a 1px white border, 59px above the line, with the time in a pill between them; dragging also covers the video with the frame at 40% on black. In a card the box is a 90px tall frame in a 2px white border, 56px above the bottom edge, with the time under it; dragging covers the card with the frame and shows the time in the middle. With a finger the frame covers the whole player or card, and the watch page's buttons step aside. A press that moves less than 3px is a click: it seeks without covering anything. The video isn't paused while dragging (pausing makes YouTube draw its own icon over the frame).

**Captions** (`lib/captions.ts`), drawn by YouTube in its own frame: we say which, where and how large. YouTube puts them at the bottom of the frame, which our crop cuts off; showing the whole frame for them brought back YouTube's title, "More videos" and logo. The embed's `track` option takes a `position` (not documented; found in YouTube's `captions.js`): a box for them, its place as parts of the frame and its size as parts of the video. The text goes by the box: wider than high, height ÷ 360 × 16px; higher than wide, width ÷ 480 × 16px (÷ 640 when it isn't 1.3 times as high), times 1 + 0.25 × `fontSize`. `captionLayout` works the box out so the text has YouTube's size and place, measured on its own pages with the same caption file (`CaptionStyle`): youtube.com, also on an iPad (2% of the height from the bottom, 70px up while the controls show), m.youtube.com, phones and Android tablets (1.5 times the text, 24px up, 48px free at the right; the controls don't move them), and the cards' previews (1.5 times). What the embed can't do: the phone site's medium weight and 8px clear border. `setOption("captions", "track", { languageCode, position })` chooses a track (asking for Bangla by name is needed: `loadModule` alone shows nothing for most of our videos, whose only captions are YouTube's own Bangla ones), `{ position }` alone only moves them (naming the track again would load a translated one again: YouTube answers "too many requests" soon), `{}` turns them off. For the first seconds (`CAPTION_NOTE_MS`) a box of the same text that reaches far above the video keeps YouTube's note "Click ⚙ for settings" out of sight (with a mouse only while they're moved up, which would cut it in half); it must be higher than wide, or its text goes by its height, and never wider than the place captions have (so in the same `fontSize` steps), or long ones in the middle leave the card. About half of the visitors get YouTube's new style (its own captions in the middle, popping on instead of rolling up), on youtube.com too. Videos without captions: the button is dimmed ("Subtitles/closed captions unavailable") and Settings has no row, as on YouTube. The CC button only changes its icon (filled when on): no line under it, no other background. On Shorts (`shortCaptionLayout`): text of width ÷ 30, in a box right under our buttons, as low as that text allows (`fontSize` 4, the largest step), because YouTube's embed gets one of two caption files for Shorts and nothing tells the page which: most visitors' place them at the bottom of their box (about a quarter down the short), some visitors' at its top, as its own pages do (the mobile site from 22px, behind its header). A box that reaches above the short all the time shows the first kind higher but hides the second: it is used only while YouTube's note may be there. Test both kinds (`apPoint` 6 and 0 in the file) after changing it. The fade at the bottom stays as it is. A size told before YouTube's captions part has loaded can get lost, so it is told again each time they are shown. The choice (on or off, language, Auto-translate) is kept for every video and Shorts; Shorts' ⋮ menu has the same list (`components/captions-dialog.tsx`). A short's captions go by its real shape (`lib/short-ratios.ts`): with 9:16 for a square one their place came out wrong. Don't take the video's shape from the player's `videoContentRect`: before the video is known it says 4:3. YouTube gives automated browsers an empty caption file on its own pages; to compare, serve a captured one (`page.route(/timedtext/)`).

### User state via localStorage

All user-generated state is persisted directly to `localStorage`:

| Key | Contents |
|---|---|
| `'sidebar-collapsed'` | Desktop sidebar state |
| `'deeni-lang-prefs'` | Auth/guest status (`{ isGuest: boolean }`) |
| `'recentSearches'` | Search history array |
| `'deeni-watch-later'` | Watch Later items (seeded with demo items on first visit) |
| `'deeni-liked-videos'` | Liked videos and shorts (seeded on first visit) |
| `'deeni-watch-history'` | Watch history, recorded by the video page, playlist player and Shorts (seeded from `lib/history-data.ts`) |
| `'deeni-playlists'` | All library playlists (seeded from `extendedPlaylists` on first visit; `videoIds` use internal ids like `"v3"`) |
| `'deeni-notification-prefs'` | Settings page notification toggles |
| `'feed-visible-channels'` | Channels shown in the home feed (`hooks/useFeedPreferences.ts`; "Don't recommend channel" removes one) |
| `'deeni-voice-lang'` | Voice search language (`en-US` or `bn-BD`), set in the voice search dialog |
| `'deeni-autoplay'` | The watch page player's Autoplay switch (`"false"` when off); also Settings → Playback → Autoplay |
| `'deeni-feed-playback'` | Settings → "Playback in feeds" (`false` turns off inline playback in cards; `lib/feed-playback.ts`) |
| `'deeni-theater'` | Theater mode on the watch pages (`"true"`) |
| `'deeni-ambient'` | Ambient mode (`"false"` when off; `lib/ambient.ts`) |
| `'deeni-volume'` | The players' volume and mute, `{ volume, muted }` (`lib/player-prefs.ts`; watch pages and Shorts, only used where there's a mouse: the watch player has no volume button on touch screens). The speed is in `sessionStorage` `'deeni-speed'`, until the tab is closed, as on YouTube |
| `'deeni-captions'` | Captions on or off, their language and Auto-translate, `{ on, lang?, translate?, from? }` (`lib/captions.ts`; watch pages and Shorts) |
| `'deeni-preview-captions'` | Captions in the cards' previews, `{ on }`: on until switched off, as on YouTube (the language is the one in `'deeni-captions'`) |
| `'deeni-watch-progress'` | How far each video was watched, `{ [youtubeId]: { t, d, at } }` (`lib/watch-progress.ts`, at most 300) |

Where a browser blocks storage (all cookies blocked, some in-app browsers), every use of it throws, which took every page down: the first script in `app/layout.tsx` puts an in-memory one in its place. `createLocalStore` takes a value of another kind (damaged data) as missing and drops empty entries from lists; other reads check what they got (`lib/recent-searches.ts`).

`hooks/useWatchLater.ts`, `hooks/useLikedVideos.ts` (both via `hooks/useSavedList.ts`), `hooks/useWatchHistory.ts` and `hooks/usePlaylists.ts` are built on `lib/local-store.ts` (`createLocalStore` + `useSyncExternalStore`), so every component shares one copy of the data and writes never use stale state. Use these hooks rather than reading/writing these keys directly. The "Watch Later" (`pl-watch-later`) and "Liked Videos" (`pl-liked-videos`) playlists are derived from their stores, not stored separately. Pages refer to the same video by internal id (`"v3"`) or YouTube id; `lib/media-lookup.ts` resolves both (`findVideo`, `findShort`, `findPlayable`: either, as a video with `isShort`), and the hooks store canonical ids. A saved item's details (title, channel, views) come from the catalogue, not from the copy saved with it. Playlists hold videos and shorts, and only what can be played, so a playlist's count is what it shows; Watch later and Liked videos count both as playlists too. `lib/language-prefs.ts` merges into `deeni-lang-prefs` without changing `isGuest`.

**Watched progress** (`lib/watch-progress.ts`), as on YouTube: the watch player saves how far a video got (every 5s while playing, and on pause, the end, leaving the video or hiding the tab; reports from before its resume seek are skipped so they can't wipe the place), and so does a card's inline playback. Every video thumbnail shows it as `<WatchedBar videoId>` (`components/watched-bar.tsx`: a 4px red bar along the bottom edge, inside the thumbnail's box, next to the duration; cards, History, related list, search, Watch Later, Liked, playlist panel, scholar page). Opening a video (from History or anywhere) goes on from that place (`resumeTime`: after a card's preview its exact time wins); under 5s, or a video watched to its last 10s (3% for long ones), counts as not started / finished: a finished one shows a full bar and starts again. Inline playback starts where the video was left (`start=` in its URL) and adds the video to History once it has played 5 seconds. Shorts have no progress.

### Shorts page (`app/shorts/page.tsx`)

The most complex file (~1800 lines), entirely `"use client"`. Key mechanics:

- **Opening a short from a link** (`/shorts?v=ID`): the starting index comes from the URL in the first render and the feed scrolls there before paint, so only that short's player loads (no jump from the first short)
- **Scroll container**: `position: fixed` (phones: from the top down to the bottom nav; desktop: below the header) with `overflow-y-scroll overflow-x-hidden touch-pan-y snap-y snap-mandatory`. It only moves up and down: the hidden action rails of the other shorts slide in from the right and must not make it pannable sideways. `AppShell` gives `/shorts` no padding or minimum height, so the page behind the feed never scrolls.
- **Each section**: `h-full` of the feed on phones, `h-[calc(100%-32px)]` on desktop (the next video peeks at the bottom); the video keeps a 9:16 aspect on desktop. Don't size sections with `100vh`: on phones it is taller than the visible screen while the browser bar shows, so shorts stop fitting the screen.
- **Title and channel** (bottom left): on phones the title ends 19px above the bottom of the video (16px above the progress bar) and the actions 27px, on every size, as on m.youtube.com (measured at 360, 393 and 412px); 24px from the bottom on desktop.
- **Action rail**: from `lg` up, like/share/save/report sit beside the video (the Comment button is commented out in `app/shorts/page.tsx`; its panel is still there) as `bg-secondary` circles with `text-foreground` icons (readable in light mode); below `lg` they sit over the video, white on a dark backing, and their size (34-48px) and gaps follow the screen's height (`svh` clamps), so the column fits under the top controls and beside the title on any phone, also an iPhone SE in Safari with its toolbars (it used to reach up under the ⋮)
- **Mobile iframe cover**: `.shorts-player-box` is a size container and `.shorts-video-iframe` (and the cover, `.shorts-poster`) is `max(100cqw, 100cqh*9/16)` × `max(100cqh, 100cqw*16/9)`, centred (browsers without container query units, e.g. Safari 15 on iPhone 7/6s/SE, get the same size from the screen: `100vw` and `100dvh - 56px - safe area`; keep it pure CSS, so the server's HTML is right before any script runs), so the 9:16 player covers the box (cropping the overflow) with no black bars at the sides. The iframe itself is 120px taller at the top and bottom (its video stays centred): YouTube's title, logo and buttons, there for a short's first seconds, are in those bands, outside the box. Captions begin under the buttons at the top (see Captions). Most phones are wider than 9:16 once the bottom nav is counted. Until its video plays, a short shows its cover (`ShortCover`): the video's first frame, YouTube's `frame0.jpg` (about 270×480; 480×480 for a square video), `object-contain` in the same 9:16 box as the video (`.shorts-poster`), so the picture doesn't change when the video starts, as in YouTube's apps and KinTube (`hbg/safekids-*`: `ShortsCover`). Without a first frame (an error or YouTube's 120×90 placeholder) it's the thumbnail. YouTube's 4:3 thumbnails, often with black strips at both sides, used to show the short smaller than its video, which then seemed to zoom in.
- **Players (instant switching, no black screen)**: the active short and its neighbours (`PRELOAD_RANGE`) have a mounted iframe. Neighbours mount 1.5s after the first short starts playing, when the browser is idle (or after 6s). Each iframe's `src` is fixed (`autoplay=0`) and never rewritten; play/pause/seek/mute go through postMessage. The next short is "primed": played muted under its thumbnail, then paused at 0, so its stream is buffered. Each short's thumbnail covers its iframe, and the iframe stays `opacity-0`, until that player reports `playerState === 1`. Keep the opacity: YouTube resizes its `<video>` while loading, which Lighthouse otherwise counts as layout shift for the page (CLS went 0.94 → 0).
- **iPhone, iPad and Safari** (`hosted`, as on the watch page): no short has a frame of its own. The shared player is attached to the short on screen (`attachHost(box, "short")`: fixed to the screen, the 9:16 video covering the box with no side bars, YouTube's bars cropped off in 120px bands above and below; it follows the feed while it scrolls) and each new short goes into it with `loadVideoById`, so the sound a tap gave it stays on while swiping (YouTube's own apps also reuse one player). The frame sits under the feed (`z-[2]`; black behind it on phones); the short's section and box turn see-through once it plays, and the frame stays hidden (`setHostVisible`) until then, behind the thumbnail. On phones a tap on a Shorts link already lays it out (invisible) over the whole screen above the bottom nav, so YouTube redraws it at that size while the page loads. It is shown with `revealHost` only once its size has been the same for 400ms (YouTube redraws its video a moment after its frame changes size or comes out of `display: none`; shown at once, a short appeared small and then zoomed to fill the screen); the watch player hides its thumbnail the same way. Messages about another video are ignored; on attach the page takes the state YouTube already reported (`hostInfo()`), since a tap may have started the short before the page existed. No automatic mute by the play watchdog here.
- **Autoplay and sound**: browsers allow sound only after a click, tap or key press on the page (wheel scrolling and swipes don't count). Each player is asked for YouTube's `onAutoplayBlocked` event (`addEventListener` command); when it fires for the active short, the short plays muted at once and a "Tap to unmute" pill shows. That automatic mute (`autoMuted`, not the visitor's choice) is undone by their next click or key press anywhere; a tap on the video then unmutes instead of pausing. Don't mute on a timer: slow-loading shorts were treated as blocked and everything after stayed muted.
- **Play watchdog, nothing stays stuck** (`watchPlayback`): until the active short plays, every second: `playVideo` again for the first 5s (commands can get lost while a player loads or seeks; muting only as a last resort), a spinner from 1s, at 10s its player is loaded again once (a new `<iframe>` key, without the preloaded neighbours; the shared player: `hostLoad(id, sound, again)`), going on from where it stopped, and 15s later the message "This short isn't playing" with Try again and Next short. Twice as long for a player that hasn't answered yet or that stopped to load while playing (slow networks). Nothing happens while the tab is hidden. YouTube's `onError` (removed, private, not embeddable) shows "This short isn't available" at once; a preloaded short's error is kept until it's on screen. Phones show a play icon while a short is paused.
- **Loop**: YouTube's `loop=1&playlist=ID` for a short's own iframe; the shared player has no playlist, so the page seeks to 0 just before the end (and on the ended state): it used to freeze on its last frame on iPhone.
- **Replaced shorts** (`replacedShorts` in `lib/shorts-data.ts`): old links to a short taken out of the feed open the one in its place. `removedShorts` (same file) lists shorts taken out for good: they are also left out of History, Liked and Watch later saved earlier in a visitor's browser, and their old links open the first short.
- **"Paused"**: the UI shows "paused" only for a real pause after the short has played (`activePlayedRef`), not for the passing states while switching.
- **Taps**: a tap within 250ms of a scroll (stopping a swipe) doesn't toggle play/pause; tapping a short that isn't active (the next one peeking in on desktop) scrolls to it.
- **Scroll detection**: `scrollend` event (Chrome/Firefox) with a 250ms debounced fallback; arrow keys and the up/down buttons switch immediately. A `scrollend` away from the key's target is ignored: Safari reports the end of a slide that a new key press cut short, which made the feed jump back a short
- **Controls visibility**: gated on `isActive && !isScrolling` for the current video; `(isHovered || isActive) && !isScrolling` for top controls
- **YouTube postMessage protocol**: iframes use `enablejsapi=1`. After an iframe loads, `{ event: 'listening', id }` is sent repeatedly until the player answers. Incoming messages are matched to the iframe that sent them (`e.source`), so only the active player drives the progress bar and play state. YouTube sends periodic `infoDelivery` messages (`currentTime`, `duration`, `playerState`). Commands are `{ event: 'command', func, args }` (`playVideo`, `pauseVideo`, `seekTo`, `mute`, …). All postMessage calls target `'https://www.youtube.com'`.
- **Progress bar**: `absolute bottom-0` inside the video container, 3px tall, red fill. `videoCurrentTime`/`videoDuration` state is reset to 0 on every video switch. `videoDurationRef` (a ref mirroring `videoDuration`) is used inside mouse/touch drag closures to avoid stale state captures. Drag-to-seek wires `mousemove`/`mouseup` on `window` and `touchmove` on the bar element.

### Every screen size

- **Phones held sideways and very low windows**: the Tailwind variant `low:` (landscape and at most 560px high; it comes before `md:`/`lg:` in the CSS, so against those it needs `low:!...`). The watch player is never taller than what shows under the header and app bar (`PLAYER_FRAME`/`PLAYER_BOX`, `PLAYER_MAX` in `components/watch-layout.ts`), the app bar scrolls away, and on Shorts the top buttons and the actions stand beside the 9:16 video.
- **Notches**: the page reaches the screen's edges (`viewport-fit=cover`), so `body` is padded by `--sal`/`--sar` (the left and right safe areas, `app/globals.css`). Anything fixed to a side needs its own: `safe-x`, or `left-[var(--sal)]`. The player's controls have theirs while it fills the window.
- **Menus and sheets** are never taller than the room there is and scroll inside (`ui/dropdown-menu`, `ui/drawer`); check new ones at 568x320.
- **Phones under 400px** (`max-[399px]:`): channels and scholars are cards, two beside each other, the picture on top (`components/person-item.tsx`; rows from 400px), names never cut; headers and the You box are stacked; the video's buttons fit without swiping. Rows' thumbnails are `ROW_THUMB` (160px, smaller under 400px); their views and time are `RowMeta` (`components/media-details.tsx`: "6mo ago" on phones), and `Dots` puts dots between a line's parts, never at the end of a line when they wrap.
- **Turning a phone**: modern phones are 768px or wider sideways, so it switches the whole page between phone and desktop. `useMediaQuery` has one listener per query for the page, which tells everyone at once; with one each, the 50+ menus updated one inside the other and React stopped ("Maximum update depth exceeded").
- **Keyboard**: phones draw it over the page; `useKeyboardInset(active)` says how much it covers (the search screen's button stays above it).
- The browser's larger text (root font size 20–24px) must fit too: rows of controls wrap (`ListHeader`).
- **Phone or desktop parts**: where the page is pre-rendered, put both in it and hide one with CSS until `useHydrated()` (the related list, the description, the bottom nav); `useMediaQuery` alone is false on the server, so phones first showed the desktop's.
- Shorts' comments and description are beside the video from 1024px (and 561px high), which shrinks to stay whole (`--feed-w`); otherwise the app's sheet.

### Bottom of the screen on phones

`MobileNav` follows Chrome's edge-to-edge guide (Chrome 135+ with `viewport-fit=cover` draws under the phone's navigation bar): `--sab-max` (`app/globals.css`) is `env(safe-area-max-inset-bottom)` (falling back to the current `safe-area-inset-bottom`); the nav is `56px + --sab-max` tall with that as padding and `bottom: calc(env(safe-area-inset-bottom) - --sab-max)`, so it always sits right above the gesture bar / Back-Home-Recents buttons / home indicator without relayout. Don't put the plain inset in `padding-bottom` (layout thrash while Chrome's bottom bar moves). `AppShell`'s bottom padding uses `56px + --sab-max`. While shown, the nav sets `data-bottom-nav` on `<html>`; toasts (`Toaster` in `app/layout.tsx`) use `--toast-bottom`, defined on the toaster element (not `:root`: changing a custom property on `:root` restyles the whole page, ~100ms TBT on the home feed): 16px above the nav when it's there, 16px above the bottom edge (plus the inset) on pages without it, 30px on desktop (YouTube's).

### Page layout (the same on every screen)

`components/page-layout.ts` has the spaces and text sizes every page uses: `PAGE` (12px at the sides on phones, 24px from `md`; `mt-14 md:mt-16` under the fixed 56px header), `PAGE_UNDER_BAR`, `PAGE_NARROW`, `PAGE_TITLE` (24px bold on every screen size), `PAGE_SUBTITLE`, `SECTION_TITLE` (18px bold, 20px from `md`), `BOX_TITLE` (16px medium), `CHIP*`, `ROW_TITLE`/`ROW_DETAILS` and `BIG_ROW_*`. Don't write these sizes out in a page.

- **The phone's app bar** (`components/page-bar.tsx`, `PageBar`): every page one step in (video, playlist, channel, scholar and its About, category, `/help/*`, `/more/*`, `/donate`) starts with it: 48px, sticky at `top-14` under the header, a 24px arrow in a 44px button and the title at 16px medium on one line; hidden from `md`. These pages put `pt-14` on the outermost wrapper and have no bottom nav (`MobileNav`'s `inner` list: keep the two in step). `parent` is where Back goes when the page was opened straight from a link (`hooks/use-back.ts`). `as="h1"` where the page shows no other title on phones, so there is always one visible `h1`. Something sticky under it uses `top-[104px]` (the profile tabs).
- **List pages**: `ListHeader` (title, line under it, search row; beside the title from `lg`), `SearchField` (the only search box: grey 40px pill), `SortDropdown` (`pill` beside a search box, `chip` in a row of chips; it says the order in use and ticks it), `LanguageChips` (only languages something is listed in, all on at first), `EmptyState`. Filter chips are 8px apart (`CHIP_ROW`).
- **Channel and scholar** (`components/profile.tsx`): one header (on phones under 400px the picture is above the name, in the middle), tabs, and Videos, Shorts, Playlists and About contents; a scholar's videos, shorts and playlists are its channel's.
- **Watch later and Liked videos** (`components/library.tsx`), **playlists** (`components/playlist-card.tsx`: the card is a link, its menu beside it), **the block under the player** on the video and playlist pages (`components/watch-info.tsx`), **text pages** (`components/text-page.tsx`), **rows that open a page** (`components/link-row.tsx`), checkboxes (`components/tick.tsx`), lengths on thumbnails (`components/duration-badge.tsx`), form fields (`components/form-field.tsx`): each is one component used everywhere.
- Data is in the bundle, so pages show it at once: no artificial waits. What is read from `localStorage` waits for hydration (`useHydrated`), behind a placeholder of the page's own shape. Pages start with padding (`PAGE`), not a top margin: a margin collapses through the page and moves the whole body when it appears. `app/error.tsx` shows in a page's place when it breaks.
- Accessibility (checked with axe): a thumbnail that repeats its title's link has `tabIndex={-1} aria-hidden="true"`; lists without sections have an `sr-only` `h2`, so headings go `h1` → `h2` → `h3`; a button's `aria-label` contains the text it shows; no control inside another; targets at least 24px; text fields `text-base md:text-sm` (iOS zooms in on smaller ones; pinch-zoom stays allowed).
- Numbers: `lib/format.ts` (`compactNumber`, `viewsText`, `countText`); a channel's subscribers `subscribersText(channelId)`. Parts of a line are separated with "•". Words are in sentence case ("Watch later", "Sign in"), and the language is "Bangla".

### UI conventions (YouTube-like)

- Font: Roboto via `next/font` (`--font-roboto`, Tailwind `font-sans`). Bangla/Arabic/Urdu text falls back to the system font.
- Colours: the tokens in `app/globals.css` use YouTube's neutrals (`muted` = #f2f2f2 / #272727 fills and chips, `accent` = hover, `muted-foreground` = #606060 / #aaa secondary text). YouTube blue (`#065fd4`, dark `#3ea6ff`) is only for the Sign in button, the search focus border and links inside descriptions.
- **Three-dot menus** are one component, `ActionMenu` (`components/action-menu.tsx`): a page only lists the actions. On phones a sheet along the bottom (48px rows, 24px icons, 15px), from `md` a menu at the button (36px, 20px, 14px). A video's or short's is `MediaMenu` (`components/media-menu.tsx`): always Save to Watch later · Save to playlist · Share first; where the app lists it (`scope="suggested"`: Home, category, channel, scholar, search, related) then Not interested · Don't recommend channel · Report; in the visitor's own lists (`scope="own"`: History, Liked, Watch later, a playlist) then the list's own actions, "Remove from …" last and red. A playlist's is `PlaylistMenu` (Play all · Share · Edit · Delete; Share only when public, Edit and Delete only for the visitor's own). An action that opens a dialog or card sets `opens`. A clickable row around a menu must ignore presses that aren't inside it (`e.currentTarget.contains(e.target)`): React sends it those in the sheet too, and stopping them instead keeps a tap above the sheet from closing it.
- Share, Report and Send feedback: `openShare(path)`, `openReport(kind, title)`, `openFeedback()` (`lib/dialogs.ts`), one dialog each for the whole app (`components/dialogs.tsx`, loaded on first use). Share and Report are sheets on phones (`ResponsiveDialog`). Share has every site of our other apps (Quran Tube, Quran Radio, Hadith) and YouTube's that take a link without a key (`lib/share.ts`: the site's own share page in a new tab, with the title; apps, such as Viber, are opened on the device and a message says so if they aren't there), in one row with arrows (`hooks/use-scroll-row.ts`, also the chips'), "More" for the phone's own share sheet, and Copy, which also works over http. Pass the title and picture: `openShare(path, title, image)`. Links are shared with their public address, also from localhost or the local network (`shareUrl` in `lib/share-path.ts`): no app can make a preview of the others. Sheets (`ui/drawer`) close when their handle is pulled down; their title is `DrawerTitleBar`. Dialogs are 16px from a phone's sides; their buttons are at the right, Cancel (`ghost`) first. Sheets, dialogs and menus share the `popover` surface.
- The dots: use `MoreButton` (`components/more-button.tsx`): solid dots (`MoreVertIcon`), 20px on phones and 24px from `md` up, in a 40px circle, always visible on cards and rows. Don't use lucide's `MoreVertical` (its dots are too small).
- Nothing stays behind after a click. Focus rings and outlines show only while the visitor uses Tab: a script in `app/layout.tsx` sets `html[data-keyboard]` on Tab and removes it on any click or touch, and `app/globals.css` hides rings (`ring-*`) and outlines without it (`:focus-visible` isn't enough: a closing menu or dialog gives focus back to its button, which browsers then outline). Text fields show focus with their border colour. For anything else that focus must not leave behind after a click, use the `kb:` variant (`kb:group-focus-within:opacity-100`), not plain `focus-within`/`focus-visible`. `hover:` applies only where there is a mouse (`hoverOnlyWhenSupported`), so a tapped button keeps no hover colour on phones; give it an `active:` state instead.
- Menus (`components/ui/dropdown-menu.tsx`) don't lock the page: it, and any list in it such as the related videos, scrolls while a menu is open, and scrolling closes the menu (`hooks/use-menu-dismiss.ts`, also used by the Shorts page's own ⋮ menu). A click outside only closes it; it doesn't also open the video under the pointer. (YouTube blocks scrolling while a 3-dot menu is open; this is friendlier.) Popups of the fixed header pass `closeOnScroll={false}`. Dialogs and bottom sheets still lock the page.
- Messages at the bottom: only through `notify(message, undo?)` in `lib/notify.ts`, never sonner's `toast` directly. Show one when the result is somewhere else (saved to Watch later or a playlist, link copied, report sent), when something was removed or hidden (with Undo: the hooks' remove functions return it), or when something failed. None when the page shows the result itself: switches, ticks, theme, a comment or playlist that appears, a filled Like button, a thank-you screen. "Not interested" and a hidden notification say so in place, with Undo. Form mistakes show at the field or keep the button disabled. One line, one at a time, sentence case, no "!". The message is a card (`components/message-card.tsx`) at the bottom left as on YouTube (16px in, 30px up; on phones above the nav, full width), dark on a light page and the other way round; about a video it carries its picture (`thumb: mediaThumb(id)`), and "Saved to ..." offers Change.
- Share and Save icons: `ShareIcon` (YouTube's curved arrow) and `SaveIcon` (its bookmark, `filled` once saved) from `components/icons/action-icons.tsx`, everywhere; not lucide's. The Save button's bookmark is filled when the video is in any playlist (`usePlaylists().isSaved`).
- Saving to Watch later: `useWatchLater().toggleWatchLater(video)` (it shows the message).
- A menu item that opens a dialog uses `<DropdownMenuItem afterClose={() => setOpen(true)}>`: the menu closes, focus returns to its button, then the dialog opens. Don't `preventDefault` in `onSelect` for this: it leaves the menu open under the dialog.
- Hover-only controls, as on YouTube: the compact lists beside the player (video page related list, playlist panel) use `MoreButton size="sm"` (20px dots, 36px circle), shown on row hover (the related list's at the row's bottom right), while its menu is open, or while the row has keyboard focus (`kb:`). History's remove ✕ is desktop-only and shown on row hover; on phones "Remove from History" is in the ⋮ menu. Always hide with the `can-hover:` variant (`can-hover:opacity-0 can-hover:group-hover:opacity-100`, defined in `tailwind.config.ts`), so touch screens, which can't hover, still show the control.
- Descriptions (videos, shorts, channel/scholar About): render with `DescriptionText` (`components/description-text.tsx`). It keeps line breaks, wraps long links with `overflow-wrap: anywhere` so they never run off the screen, and turns URLs and #hashtags into links. On phones the video and playlist pages open the full description as a bottom sheet (`Drawer`).
- Sizes: page titles 24px bold, card/list titles 16px medium (14–15px on phones), secondary text 12–14px. Avoid text under 12px except the 10px nav labels.

### Route patterns

- `/` — home feed
- `/videos/[slug]/[id]` — video detail (no desktop sidebar but the menu over it, full-width player). The address is `/videos/<title in Latin letters>/<YouTube id>`, e.g. `/videos/islamic-halaka-shesh-jamanar-fitna-prof-dr-mohammad-monzur-e/XVscS6piz9A`: readable and clean to share (no `%20` or `%E0%A6…`). Always build links with `videoPath(video)` / `videoPathForId(id)` from `lib/video-url.ts` (the slug comes from `slugify` in `lib/slug.ts`, which writes Bangla in Latin letters). Only the id finds the video; the layout permanently redirects any other slug or the internal id (`/videos/x/v2`, old channel-name links) to the readable address, and sets it as the canonical URL
- `/search/[slug]/[id]?q=…` — a search result, opened in the search page: the same page and player as `/videos/[slug]/[id]` (`components/watch-view.tsx`, `inSearch`), only its address differs. Both search routes render `components/search-view.tsx`, and the address says what shows: opening a result only changes the address with `window.history.pushState`, so it's there at once with no request, also in dev (links: `onNavigate`). Its related and next videos open in the video page (`/videos`), as everywhere; Back goes to the search's video and then to the results where they were left, the header keeps what was searched, and the canonical URL is the one under `/videos`. Build these links with `searchVideoPath(video, search)`; `isVideoPath(pathname)` says whether a page is either of them (sidebar overlay, no bottom nav). A video page opened in the app draws the player and the first related rows first, the rest of the list right after (`useAfterFirstPaint`)
- `/playlists/[slug]/[id]` — playlist detail (no desktop sidebar)
- `/shorts`, `/shorts/<id>` — vertical shorts feed (fullscreen, header auto-hides)
- `/channels/[slug]`, `/scholars/[slug]`, `/categories/[slug]` — entity detail pages. Both scholar routes render `app/scholars/[slug]/scholar-view.tsx`, which shows the profile or the About page from the URL; the About tab switches with `window.history.pushState` (Next.js syncs it with `usePathname`), so the About page opens instantly with no request, even in dev
- `/signin` — auth page (no desktop sidebar)
- `/you`, `/history`, `/liked-videos`, `/watch-later` — account/activity pages
- `/more`, `/settings`, `/help` — utility pages (each has sub-pages under the same prefix)
- `/donate`, `/search`, `/playlists` — standalone pages

### Search engines and shared links

`lib/seo.ts` (`pageMeta`, `videoMeta`, `shortMeta`, the schema.org data) and `lib/site.ts` (the site's own address: `NEXT_PUBLIC_SITE_URL`, else the project's production domain on Vercel, else https://deeni-tube-web.vercel.app for a build; previews are kept out of search engines). Every route's `layout.tsx` calls `pageMeta` with a title, a description of 50–165 characters, its path (canonical) and a picture: videos and shorts YouTube's 1280x720 one (`lib/media-meta.ts`, generated with their real publishing dates by `npm run storyboards`), playlists their first video's, the rest a card in `public/og` (`npm run og`, 1200x630). Structured data (`components/json-ld.tsx`): WebSite and Organization everywhere, VideoObject, ProfilePage, ItemList and breadcrumbs. The visitor's own pages and unknown playlists are `noindex`. `app/sitemap.ts` (with videos), `app/robots.ts`, `app/manifest.ts`. A short is shared as `/shorts/<id>` (`app/shorts/[id]/page.tsx`: the Shorts feed opened at it, so the link shows its picture; `sharePath` in `lib/share-path.ts`); in the app links stay `/shorts?v=<id>`. Use `isShortsPath(pathname)` for both. `e2e/seo.spec.ts` checks every page in the sitemap: add a new page there.

### Page titles and 404s

Pages are client components, so they can't export `metadata`. Each route has a small server `layout.tsx` that sets the title (the root layout adds the `"%s - Deeni.tube"` template). The `[slug]`/`[id]` layouts for channels, scholars, categories and videos also call `notFound()` for unknown ids, which renders `app/not-found.tsx`. Unknown ids return a real 404. These layouts also export `generateStaticParams`, so every video, scholar (and About), channel and category page is pre-rendered at build time: `<Link>`s prefetch them in full and clicks open them without a server round trip (other URLs, such as `/videos/x/v2`, still render on demand). Don't add an `app/loading.tsx` (or a `loading.tsx` above these layouts): it starts streaming before the check, which turns the 404 into a 200. `/search` and `/shorts` wrap their content in `<Suspense>` because they call `useSearchParams()`. The favicon is `app/icon.png` (cropped from the logo).

### Image loading (measured with Lighthouse, mobile + desktop)

- Load **only one** image per page early: the main (LCP) image, via `imagePriorityProps(...)` / `priorityForIndex(index)` from `lib/image-priority.ts`. Loading several images early made LCP worse on mobile: they compete for bandwidth, and pages that render a hidden desktop/mobile copy of a list download the hidden copy's eager images too.
- Default is `preload` + high priority (React starts the download during render, which helped the heavy client-rendered lists). Watch Later and Liked measured better with `{ preload: false }` (eager + high priority). Don't add early loading to the video page's related list; it measured no better. On the watch pages the main image is the player's thumbnail (preloaded). Video and short cards call `warmYouTube()` (`lib/warm-youtube.ts`) on hover/touch to preconnect to YouTube before the click. On Shorts only the first short's cover (its first frame) loads early (it is the main image until the player starts; mobile LCP 2.6s → 2.3s).
- `youtubeThumb(id, "small")` (320 px) is only for images up to ~170 CSS px wide where the page has no hidden duplicate using the larger size; otherwise use the default 480 px version so both copies share one download.
- The header logo uses `public/logo-header*.webp` (sized for the header); the original PNGs are kept for other uses.
